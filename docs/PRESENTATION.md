# 프로젝트 설명과 화면 안내

## 3분 설명 순서

1. **문제와 서비스 (30초)** — 브라우저 두 개에서 같은 게임을 진행하면서 카드·차례·잔액을 일치시키는 서비스다. 멀티플레이 화면으로 시작한다.
2. **실시간 통신 (40초)** — REST는 인증과 방 관리, STOMP/WebSocket은 액션과 상태·대화 전달에 사용했다. 대기실 및 방 채팅 화면과 준비 상태를 보여준다. 단순 주기적 조회로 게임을 구현한 것이 아님을 설명한다.
3. **정합성과 복구 (50초)** — 서버가 베팅과 결과를 결정하고 게임 상태·잔액을 함께 저장한다. 동일 카드와 99,000칩이 표시된 재시작 전후 화면을 비교한다. 복구 후 일시정지와 명시적 이어하기의 이유를 설명한다.
4. **변경과 전달 (40초)** — MAX 단위 오류와 방장 권한 문제를 수정한 PR, 검증 후 SHA 이미지 생성, OIDC/SSM 배포, HTTPS 상태 검사 순으로 보여준다. 릴리스 실행 자체는 수동이며 나머지 단계가 자동임을 설명한다.
5. **한계 (20초)** — 단일 백엔드 구조와 비영구 채팅, 부하 시험 미수행을 명시한다. 참여 중단 제어와 작은 화면 개선을 다음 과제로 제시한다.

## 이미지 캡션

- `01-lobby-chat.png`: 방에 들어가기 전에도 같은 로비의 사용자가 메시지와 이모지를 주고받는다.
- `02-room-chat.png`: 같은 방에 참가한 사용자 사이에서 대화가 전달된다.
- `03-ready.png`: 참가자 준비 상태를 공유하고 방장에게 시작 제한시간을 표시한다.
- `04-multiplayer.png`: 서버가 배분한 서로 다른 패와 베팅 차감 결과를 표시한다.
- `05-recovery.png`: 재시작 후 카드·베팅·잔액을 유지하고 게임을 일시정지 상태로 복원한다.
- `06-actions.png`: 한 릴리스에서 검사·이미지 게시·원격 배포가 모두 성공했다.
- `07-bet-controls.png`: 증감·직접 입력·최소 베팅·MAX로 금액을 조절한다.

## 질문에 답할 근거

| 질문 | 설명할 내용 |
| --- | --- |
| 클라이언트가 잔액을 조작하면? | 서버 인증 주체와 저장된 잔액을 기준으로 금액/차례/상태를 검사한다. 접근 제어 검사를 함께 수행한다. |
| 재시작 중 시간이 지나면? | 저장된 진행 상태를 일시정지로 복원하고 이어하기 때 새 제한시간을 준다. |
| 왜 여러 서버로 확장하지 않았나? | 현재 브로커와 게임 상태 관리가 단일 서버에 맞춰져 있다. 확장에는 메시지 브로커와 소유권/타이머 조정 설계가 추가로 필요하다. |
| 배포에 장기 AWS 키가 필요한가? | GitHub production 환경과 제한된 OIDC 역할을 사용해 일시 자격을 받는다. |
| 완전히 검증했나? | 자동 검사와 실제 배포 점검 범위를 제시하고 부하/고가용성/외부 OAuth는 제외했다고 답한다. |

정확한 실행 링크와 환경 구분은 [검증 기록](VERIFICATION.md)에 있다. 공개 자료에는 비공개 백업이나 인증 파일을 넣지 않는다.
